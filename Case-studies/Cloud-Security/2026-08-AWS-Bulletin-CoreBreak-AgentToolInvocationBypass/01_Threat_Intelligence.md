# Threat Intelligence Report
## 2026-08-AWS-Bulletin-CoreBreak-AgentToolInvocationBypass
**Date:** 2026-08-10 | **Source:** Black Hat USA 2026 disclosure (2026-08-06) | **Severity:** Critical | **Category:** AI-Governance / Cloud-Security

## Executive Overview
In a normal AI agent workflow, the agent SDK sends the user's request, system prompt, conversation history, and available tool definitions to the underlying model. The model decides whether to invoke a tool and returns a structured instruction naming the tool and its arguments; the SDK then executes that instruction. Researchers Hedi Ingber and Aviyam Ivgi found that the runtime in several major agent platforms did not verify *provenance* between "the model decided to call a tool" and "the tool was executed" — the runtime accepted data that was merely *shaped like* a model-generated tool call as sufficient authority to execute it, without confirming a legitimate model turn actually produced it. They named this cross-platform pattern "CoreBreak" and presented it publicly at Black Hat USA 2026 on 2026-08-06, with technical detail sufficient for a skilled adversary to reconstruct exploit paths even though full working exploit code was withheld from public release.

## Technical Details
- **CVE IDs and CVSS:**
  - CVE-2026-18830 — Amazon Bedrock AgentCore InvokeHarness API — CVSS v4.0 8.6 — Improper Input Validation
  - CVE-2026-18236 — Google Agent Development Kit (ADK) for Python < 2.5.0 — CVSS v4.0 9.3 — Incorrect Authorization (CWE-863)
  - CVE-2026-64650 — Vercel @ai-sdk/harness-codex < 1.0.29 — CVSS v4.0 6.3 — Incorrect Authorization (CWE-863)
  - CVE-2026-64651 — Vercel @ai-sdk/harness-opencode < 1.0.28 — CVSS v4.0 6.3 — Incorrect Authorization (CWE-863)
- **AWS path:** An authenticated remote user could place a tool-use content block in the final message of an InvokeHarness request; the event loop dispatched the named tool directly without a model turn. AWS added server-side validation rejecting caller-supplied tool-use blocks before they reach the event loop — fix applied automatically, no customer action required. Note: the underlying open-source Strands Python SDK, which AgentCore's harness is built on, retains a comparable model-skipping code path (`_has_tool_use_in_latest_message` in `event_loop.py`); AWS has classified this as falling under the customer's shared-responsibility scope and published documentation guidance rather than a code fix for standalone Strands deployments.
- **Google path (two distinct issues):** (1) CVE-2026-18236 — the confirmation processor for tools flagged as requiring human approval did not verify the target tool matched the tool actually requiring confirmation, nor that name/arguments matched the original recorded call, allowing an attacker who can manipulate session-history events to forge approval; fixed via added verification checks. (2) A related, non-default resumable-mode issue (same ADK 2.5.0 release, 2026-07-16) allowed user-authored events containing function_call parts to bypass the model and directly execute registered tools; Google now rejects function calls in user-authored messages. The public CVE record covers only the confirmation-forgery path (default configuration); the resumable-mode issue is a separate, non-default-feature fix without its own CVE.
- **Vercel path:** The harness relay trusted any process whose command line contained the path of an approved helper script as sufficient authorization. Malicious code already running inside the sandbox (e.g., via a malicious dependency or build/lifecycle hook) could satisfy that check and invoke host-exposed tools — secret lookups, deployment operations, cloud API calls — without a model-authorized event. This is a local sandbox-to-host bypass, distinct from AWS's remote-request path; exploitation requires Linux, an active harness session with at least one host-provided tool, and untrusted code already executing in the sandbox.
- **Exploitation Status:** No confirmed use against a live deployment reported by the researchers or vendors as of the Black Hat presentation. All three vendors received advance disclosure and shipped fixes before or at public presentation.
- **MITRE ATT&CK / ATLAS relevance:** Maps to MITRE ATLAS's ML Model Access and broader agentic-AI supply-chain tactics (bypassing model-level guardrails entirely); classified under CWE-863 (Incorrect Authorization) for Google and Vercel findings, and Improper Input Validation for AWS.

## Affected Technology Context
This finding matters more as a *pattern* than as three or four individual CVEs: it demonstrates that "the model approved this" is not a safe assumption to build authorization logic around in agentic AI systems, because multiple independent vendor implementations made the same category of mistake — trusting the *shape* of tool-call data rather than verifying its *provenance*. This is explicitly not prompt injection: there is no probabilistic model to fool, and a stronger, better-aligned model provides zero additional protection, because the model is bypassed entirely in the vulnerable paths. Any organization building or deploying agentic AI systems — not just users of these three specific platforms — should treat this as a design-review prompt: does our agent architecture bind tool execution to a verified, single-use, model-originated authorization token, or does it trust caller-supplied data that merely resembles one?
